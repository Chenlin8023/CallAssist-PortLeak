## 一、本轮结论（一句话）

SpringBoard 不注入、装了就进安全模式，根因是 **arm64e 链路**。经过一整轮攻坚，已把 dylib 二进制层
的已知三层坑全部填平（架构 → PAC 格式 → 转换器破坏认证），最终产出了与 BioProtect 原版逐字节同形的
**原生 roothide 包**；但该包在设备上**仍进安全模式**，说明还有一层在 dylib 二进制之外的因素没定位到。

## 二、三层根因（已全部确认并解决，勿重走）

### 第 1 层：架构（arm64 单切片被拒载）

- SpringBoard 是 **arm64e 进程**（崩溃日志 `procName=SpringBoard modelCode=iPhone16 cpuType=ARM-64`），
  只加载 arm64e 切片；arm64 单切片被 dyld 静默拒载（无日志、无崩溃、无任何痕迹）。
- 证据：BioProtect 原版是 FAT arm64+arm64e(`0x80000002`)，能进 SB；我们的 2.0.5 是 thin arm64，进不了。
- 解决：`Makefile ARCHS = arm64 arm64e`。

### 第 2 层：chained fixups 格式（ptr_format=1 非 arm64e auth）

- clang 11/13 的 arm64e target 是旧 ABI（cpusubtype `0x2`），即使 patch object/dylib 的 cpusubtype 成
  `0x80000002`，ld 产出的 chained fixups 仍是 **ptr_format=1（普通）** 而非 **12（arm64e auth）**，
  数据指针（__cfstring isa、函数指针）无 PAC 重定位 → arm64e 进程解引用即崩。
- 解决：换 **clang 19（L1ghtmann v19.0.0）+ ld64 956 + ldid(Procursus)**，原生产 cpusubtype `0x80000002`
  + ptr_format=12。该工具链要求 **glibc 2.38 = Ubuntu 24.04**（已把 WSL Ubuntu 22.04 升到 24.04）。

### 第 3 层：转换器改写 + 重签破坏 PAC

- 实测：ldid 重签会重新生成 CodeDirectory，**却不重算 arm64e 的 auth PAC**（chained fixups 数据 md5 不变、
  CodeDirectory md5 变）→ 认证失效 → dyld 拒载进安全模式。
- RootHide 转换器会改写 rootless 包的 `/var/jb` rpath 字节再重签 → 就是它破坏了 PAC。arm64 切片无 auth 所以
  不受影响（这解释了 Filza/Sileo 能加载、SpringBoard 必崩）。
- 解决：**打原生 roothide 包**（与 BioProtect 原版同形，跳过转换器）。

## 四、结果与第四层未知因素

原生 roothide 包**仍进安全模式**（用户 2026-10-24 归档时反馈）。这说明问题可能不在 dylib 二进制层，
待下次用「装这版之后的新崩溃日志」定位。

1. **转换器仍被触发**：Sileo/RootHide 可能对 iphoneos-arm64e 包也自动做了转换（用户习惯性转换，或环境强制）。
   → 验证：装完后查设备上 `/var/jb/Library/MobileSubstrate/DynamicLibraries/BioProtectLeakGuard.dylib`，
   与构建产物比对 md5；若不同 = 被转换过 = 还是转换器破坏 PAC。若是，需要换「完全绕过 Sileo 转换」的装法
   （手动 dpkg -i 到 jbroot，不经过 RootHide 的包管理器）。
2. **dylib 代码本身的 arm64e 兼容性**：MSHookFunction 在 arm64e 下的调用、我们的 hook 逻辑在 arm64e 下的行为。
   → 验证：崩溃日志的异常类型 + 崩溃 dylib。
3. **加载器/过滤器层面**：ElleKit 对 iphoneos-arm64e 原生包的处理、plist 过滤器。

**必须拿到的新证据（下次第一步）**：装原生 roothide 包之后的崩溃日志（SpringBoard 的 .ips，时间戳在装这版之后）。
