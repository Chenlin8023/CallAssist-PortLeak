## 一、一句话结论

2.0.13 真机日志证明 powerdxpc 回收已生效（xpcA≈xpcF，差仅 33），主泄漏消除；
但**空闲期 ports 仍 +6.6/分钟**，同期 xpc 驱动者 `all-system(nosb)` 恰好 +6.7/分钟
——残余是 Foundation 系匿名连接（siri.uaf/backlightd 等），不在写死的 powerdxpc
回收范围内。2.0.14 不盲目扩大回收（那些是系统自身连接，动了会坏功能），而是
①把趋势做成一眼可见的指标，②把回收名单做成可配置，将来有新证据时改配置即可。

  后段已放缓），**不是急迫泄漏**，先观察不动手。

## 三、2.0.14 改动（源码 5 处，行为默认零变化）

1. **stat 行新增 `p5=`**：本周期 ports 净增量（与 xpc5 同口径）。以后判断残余
   趋势只看 p5，不用再手算两条累计曲线的斜率差；
2. **回收名单可配置**：`config.plist` 新增
   `XPCReclaimServices`（NSArray 或 "a,b c;d" 单串均可；**前缀匹配**，如
   `com.apple.iokit.power` 覆盖同族服务）。默认仍仅 `com.apple.iokit.powerdxpc`
   ——升级后行为与 2.0.13 完全一致；
3. **安全条件不变**：仍要求「直接调用方是系统框架 + 栈回溯找到插件驱动者」，
   SB 自身、纯系统路径、插件直连的长活连接一律不碰（这也是为何 siri.uaf 这类
   系统自驱连接即使加进名单也不会被回收——它们找不到插件驱动者，天然免疫）；
4. 启动日志输出回收名单（`xpc 回收: … 目标=插件驱动的 [a|b] 连接，前缀匹配`）
   与 xpc 开关/宽限，配置是否生效一目了然；
5. 版本串、control（Version/Description）、build.sh 断言同步 2.0.14。

## 五、真机验证（装 2.0.14 → respring → 正常用机）

1. boot 块应出现「xpc 回收: 就绪（宽限 10s，目标=插件驱动的
   [com.apple.iokit.powerdxpc] 连接，前缀匹配）」；
2. stat 行出现 `p5=`：亮屏期个位数~几十、锁屏期趋 0 → 与 2.0.13 结论一致，
   主泄漏持续被兜住；p5 若连续多日稳定为正且 >10/周期，再考虑把对应服务名
   加进 `XPCReclaimServices`（届时用 top xpc / 驱动者表先定责）；
3. `xpcA` 与 `xpcF` 应继续保持同步增长、差值个位数~几十。

## 六、给未来的自己

- 「残余增长要不要收」的判据写进了 p5：**趋势可量化后再决定动不动手**，
  系统自驱连接（找不到插件驱动者）无论名单怎么配都不会被回收，这是设计而非遗漏；
- 配置示例（需要时才写）：
  `XPCReclaimServices = ( "com.apple.iokit.powerdxpc", "com.apple.backlightd" );`
