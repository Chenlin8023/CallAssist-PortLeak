## 一、一句话结论

2.0.8 真机运行完美（定时器修复生效：影子自验证 ok、stat 行每 5 分钟一条），
数据同时给出两个决定性事实：**① ports 以 ~300/分钟（5.3/秒）线性上涨**，
照此速率 6-7 小时触顶 131072 被杀（与历次 10.7 小时存活吻合）；
**② `paBP=0` 且 `pa`（mach_port_allocate 总数）增速仅为 ports 增速的 1/3**——
BioProtect 从未直接分配过端口，04/05 报告的「CFUserNotification 应答端口泄漏」
假设被真机数据排除（cf_called 全程 0），**约 2/3 的新端口走
`mach_port_allocate` 之外的创建机制**（mach_port_construct / xpc 连接 /
内核注入的 send-once 权）。真凶大概率是 SB 里 40+ 插件中的某一个在反复建
XPC 连接或发未应答 RPC。

## 三、2.0.9 归因升级（构建完成）

在不动修复引擎的前提下加三层观测，下一份日志直接点名泄漏者：

1. **端口类型分解**：`mach_port_names` 返回的类型位分类为
   `tS/tR/tO/tD/tP`（send / receive / send-once / dead / port-set）。
   - tO 涨 → 未应答 RPC（reply port）泛滥，查谁在发消息不等回复；
   - tR 涨 → 进程内自建端口不释放（construct/allocate 路径）；
   - tS 涨 → 持有指向外部的 send 权不释放（XPC 连接对象泄漏典型形态）。
2. **mach_port_construct + mach_port_allocate_full 钩子**：总量 + Top8
   调用点（`镜像+偏移:次数`，top construct 行）。
3. **xpc_connection_create / _create_mach_service 钩子**（dlsym 取址，
   不给 dylib 增加 libxpc 依赖）：Top10 `镜像/服务名:次数` 直方图（top xpc 行）。

钩子内只做原子计数 + 缓存查表，不做 IO；xpc 钩子失败不影响其余功能。

## 五、验证与判读（装 2.0.9 → respring → 30 分钟后看 guard.log）

1. 常规三跳不变：installed 标记 → crumb.log 三行 → 影子自验证 ok；
2. 每条 stat 行新增 `pc=` `mpaf=` `xpc=`（三个创建口的累计计数）与
   `tS/tR/tO/tD/tP`（当前端口构成）；
3. 判读表：
   - **tO 增长最快** → 未应答 RPC；看 `top xpc` 行里谁的服务名出现次数最高；
   - **tR 增长最快** → 自建端口；看 `top construct/alloc_full` 行的镜像+偏移；
   - **tS 增长最快** → 外发连接泄漏；同样看 top xpc；
   - `xpc=` 猛涨且 top xpc 里某插件名反复出现 → **直接锁定该插件**，
     下一轮针对性 hook 它的连接释放，或建议用户卸载/禁用该插件对照。
4. 止血（可选）：`/var/mobile/Library/BioProtectLeakGuard/config.plist` 把
   `EnableAutoRespring` 改 `true` → 端口超阈值且锁屏时自动受控重启桌面，
   白天使用不会被 jetsam 突然强杀（默认关，因为要观察数据）。
5. 30-60 分钟后把 stat/top 行段抄回（或整个 guard.log），即可进入定责阶段。

## 六、注意

- ports 从 2856 起步偏高是正常的：SB 启动即有数千端口；
- 2.0.8 期间未发生被杀（观察窗口只有 95 分钟），2.0.9 装上后如需长时间观察可开止血开关；
- BioProtect 本体的 CFUserNotification 泄漏并非不存在（逆向确认代码路径无释放），
  只是本机使用场景触发频率极低（cf_called=0），**当前主因不在它**——修好的 CF 回收
  继续保留，属于防御性兜底。
